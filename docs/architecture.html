01

Requirements analysis — what the spec gets right, and what's missing

The spec is unusually complete for a first pass. The five product areas are coherent, the AI-as-estimate framing is correct, and asking for a normalized schema up front avoids the mistake most trackers make. What follows is the delta: things that will bite during implementation if they aren't decided now, ordered by how expensive they are to retrofit.

Gaps that change the schema — decide before the first migration

Offline-first is not optional Missing

People log food in supermarket basements and lift in gyms with no signal. An online-only app fails at exactly the moment of use. This affects every table (client-generated UUIDs, updated_at, soft deletes, an outbox) and is brutal to retrofit.

Nutrient snapshots on log rows Missing

If a log row only references food_id, then editing a food silently rewrites history — yesterday's 2,100 kcal becomes 2,400. Every food_logs row must carry a frozen copy of the nutrients as logged.

Local-date vs. UTC Missing

"Which day does this belong to?" must be resolved in the user's timezone at write time and stored as a plain date. Deriving it from a UTC timestamp puts an 11pm snack on tomorrow, and breaks again when they fly.

Units: metric and imperial Missing

Store canonical SI everywhere (g, ml, kg, cm), convert at the display boundary only. Mixed storage units are the single most common source of corrupt fitness data.

Product decisions the spec leaves open

QuestionWhy it mattersMy recommendation
Where does "calories burned" come from? The dashboard shows it but nothing produces it. Options: MET-value estimate per exercise, or import from Apple Health / Health Connect. MET-based estimate per exercise (stored on exercises.met), plus optional health-platform import that overrides it.
Does exercise add calories back to the budget? Changes the core dashboard maths. MyFitnessPal says yes; most coaches say no because burn estimates are inflated. Make it a user setting, default off. Show burn as a separate stat, not as budget.
Guest mode, or signup wall? A signup wall before any value is seen typically halves activation. Anonymous session on first launch; prompt to link an account when they have data worth keeping.
Free vs. premium AI scans have real per-call cost. If they're unlimited and free, cost scales with usage and nothing recovers it. Decide the boundary now even if you ship free — put a server-side quota check in from day one.
Language(s) at launch You're in Switzerland: DE/FR/IT matter, and food names are per-locale data, not UI strings. English-only UI at launch, but design foods.name_i18n jsonb now so it isn't a migration later.

Legal and store-review items Not in spec

Food data licensing

This constrains the schema. USDA FoodData Central is public domain — safe for anything. Open Food Facts is ODbL: excellent EU barcode coverage, but requires attribution and share-alike on the database. Commercial APIs (Nutritionix, Edamam, FatSecret) are paid and forbid redistribution. Add foods.source and foods.license from the first migration.

Health data is a sensitive category

GDPR / Swiss nFADP apply. You need a privacy policy, App Store privacy labels, data export, and hard account deletion (App Store guideline 5.1.1(v) makes deletion mandatory once you have accounts). Meal photos leaving the device to a model provider must be disclosed, and the provider contract must exclude training on your data.

Calorie-goal safety floors

Apple and Google both scrutinise calorie trackers for eating-disorder risk. Clamp goals at a floor (commonly 1,200 kcal for women, 1,500 for men) with an explicit warning, cap deficit rate at ~1 kg/week, and carry a "not medical advice" disclaimer. Age-gate 16+.

AI accuracy framing

Your spec already says estimates must be labelled as estimates — good. Make it structural, not a one-off string: a provenance chip (verified / estimated / you entered this) rendered by a shared component wherever a number appears.

Features worth building that the spec omits Later phases

  • Copy / repeat meals — "same as yesterday", recent & frequent foods, multi-select add. This is the single biggest retention feature in every successful tracker, and it's cheap once the schema is right.
  • Quick-add calories — log 350 kcal with no food attached, for restaurant meals.
  • Cooked-weight yield on recipes — 500 g raw becomes 400 g cooked; without a yield field, per-gram density is wrong.
  • Training extras — supersets, rest timer, previous-set hints in the logging row, estimated 1RM, automatic PR detection, plate calculator.
  • Streaks and reminders — hydration nudges and a logging streak; the retention lever for a daily-use app.
  • Do other drinks count as water? — a coffee logged as food optionally contributing to hydration.

03

System architecture

Three tiers, with a hard rule: the mobile app never holds a secret and never talks to a model provider directly. Everything privileged goes through an Edge Function authenticated by the user's Supabase JWT.

Presentation Expo Router screens · design-system components · Reanimated transitions. Screens hold no business logic — they call feature hooks.
Feature logic Per-domain hooks and services (useDiaryDay, logFood, estimateBurn). Pure, unit-testable, no React Native imports where avoidable.
Data access Drizzle repositories over SQLite. Single source of truth for reads. The UI never queries the network directly.
Sync engine Outbox push + delta pull against Supabase, on a cursor of updated_at. Runs on app foreground, on connectivity regain, and after each mutation.
Edge Functions Deno, deployed with Supabase. Holds every secret. analyze-label, analyze-meal, barcode-lookup, account-delete, export-data.
Postgres Normalized schema, row-level security on every user-owned table, full-text + trigram search, SQL functions for the aggregation-heavy reads.
External Model provider (label + meal vision) · Open Food Facts / USDA (food data) · Apple Health & Health Connect (optional) · RevenueCat (if monetised).

The read path that matters most

The dashboard and diary are opened many times a day, so they get a dedicated path. Rather than fetching rows and summing in JavaScript, the day's totals come from a single indexed query over food_logs, water_logs and workouts filtered by (user_id, logged_on) — locally in SQLite, so it works offline and returns in under a frame.

04

Database design

Twenty-two tables across six domains. Three modelling decisions drive everything else, and they're the ones worth reviewing carefully.

1 · Canonical base units

Every food stores nutrients per 100 g or per 100 ml (or per item, for countable foods). Human portions live separately in food_servings ("1 medium apple = 182 g"). Everything logged resolves to grams or millilitres internally.

Makes recipes, scaling and aggregation trivial, and eliminates unit ambiguity at the source.

2 · Nutrients in a sibling table

Fixed columns in food_nutrients (1:1 with foods), not an EAV key/value table. The nutrient set is small and fixed, and every query wants all of it at once.

Keeps foods narrow for search, and a micros jsonb column absorbs vitamins later without a migration.

3 · Goals as validity ranges

Not one row per day. goal_periods has effective_from / effective_to, so history is preserved and a year costs a handful of rows instead of 365.

A SQL function goals_for_date() hides the range lookup from callers.

Search

Food search is the interaction users touch most, and generic ILIKE '%query%' makes an app feel cheap. A single Postgres function ranks results, mirrored by an equivalent FTS5 query locally:

  1. Exact barcode match
  2. Foods this user has logged recently (recency-weighted) — the reason good trackers feel fast
  3. This user's own custom foods and recipes
  4. Verified branded foods, by full-text rank
  5. Generic catalogue foods, with trigram fuzzy match to survive typos

Indexes: GIN on search_tsv, pg_trgm on name, unique on food_barcodes.barcode.

Row-level security

RLS enabled on every table, no exceptions. User-owned tables get using (auth.uid() = user_id) for all four verbs. The catalogue tables take a split policy: shared rows (owner_id is null) are readable by everyone and writable by no one; owned rows are readable and writable only by their owner. Imports run through the service role, which exists only inside Edge Functions and never in the app bundle.

Test it, don't assume it. RLS policies are code and can be wrong. The test suite should include a suite that authenticates as user A and asserts a zero-row result for every one of user B's tables.

05

AI architecture

Two features, one pipeline. The design goal is that a wrong model output is always a recoverable UI state and never a corrupt database row.

  1. DeviceCapture — photo taken, then downscaled to ~1600px on the long edge and re-compressed. Cuts upload time, latency and token cost substantially with no measurable accuracy loss on labels.
  2. Device → StorageUpload to a private bucket at {user_id}/{scan_id}.jpg, guarded by a storage RLS policy. Uploading before invoking gives you retries, an audit trail, and the ability to re-run extraction later without asking the user to re-shoot.
  3. Edge FunctionInvoke analyze-label or analyze-meal with the storage path — never the image bytes. Function verifies the JWT, checks the user's quota, and hashes the image to short-circuit repeat scans.
  4. Edge FunctionExtract — the provider adapter calls the model with a structured-output schema, so the response conforms by construction rather than by prompt-begging.
  5. Edge FunctionValidate against the shared Zod schema. On failure, one retry with the validation error fed back. On second failure, return a typed error — never a partial object.
  6. PostgresPersist to ai_scan_results with status succeeded. Nothing has touched the diary yet.
  7. DeviceConfirm — the user sees every extracted field, editable, with per-field confidence surfaced. Low-confidence fields are pre-focused rather than silently accepted.
  8. PostgresCommit — on save, a food_logs row is written with source = 'ai_label' | 'ai_photo', and the user's edits are diffed into ai_scan_results.user_corrections.

Provider abstraction

One interface, implementations per vendor, selected by an environment variable inside the Edge Function. Feature code never names a vendor.

Model selection

The two tasks have different difficulty profiles, so they shouldn't share a model by default. Label extraction is constrained OCR-plus-structure — a smaller model handles it accurately at a fraction of the cost. Meal estimation is genuinely hard visual reasoning (identify foods, estimate portions from perspective, recall nutrient densities) and deserves the strongest model.

Concretely: start both on claude-opus-5 to establish an accuracy ceiling, then measure whether claude-haiku-4-5 holds that accuracy on labels — it is roughly a fifth of the cost. Make the model a per-task config value so this is a deployment change, not a code change. Structured outputs go through output_config.format with a JSON schema, which is what makes step 5 above a formality rather than a gamble.

Cost, abuse and quality control

Quotas

Per-user daily scan limits enforced in the Edge Function against ai_usage, before the model call. This is also where an entitlement check goes if you monetise. Never enforce a limit client-side.

Deduplication

Hash the image; if the same label was scanned before, return the cached extraction. Barcode-adjacent labels repeat constantly across a user base.

Prompt caching

The extraction instructions are long, stable and identical on every call — cache the prefix and only the image varies. Meaningful cost reduction at volume, for no behavioural change.

Golden-set evals

A fixture set of label photos with hand-verified ground truth, run in CI against per-nutrient tolerance thresholds. Without this, every prompt change is a blind change. user_corrections feeds this set over time.

Meal-photo estimates need honest UI. Portion estimation from a single photo without a size reference is inherently imprecise — a plausible error band is ±25–30%. Show a range rather than a single number, keep the wording as an estimate throughout, and make the portion slider the primary interaction on the confirm screen so correcting it feels expected rather than corrective.

Navigation and screens

Your five tabs are right. Two refinements:

  • "Diary" rather than "Food" — the tab is a day view, and naming it for the day is what makes the mental model click.
  • Scan is an action, not a destination. Tapping the centre tab opens a sheet offering Barcode · Nutrition label · Meal photo · Quick add, then goes straight to the camera. Landing on a hub screen that only contains four buttons is a wasted tap on the app's most-used shortcut.

Design direction

Every screen ships with four states designed, not three: loading (skeletons that match final layout, never spinners), empty (with the action that fills it), error (what happened and what to do), and populated. Numeric input uses a purpose-built keypad rather than the system numeric keyboard — logging 87.5 kg between sets should take one thumb and under a second.

Accessibility is not a later phase: dynamic type support, VoiceOver labels on every interactive element, 44pt minimum touch targets, contrast checked in both themes, and prefers-reduced-motion respected.

08

Security

Secrets

Model API keys and the Postgres service-role key exist only as Edge Function environment variables. The app bundle holds the Supabase URL and the anon key — both are public by design and useless without a valid JWT plus RLS.

Anything in EXPO_PUBLIC_* ships in the binary and is readable by anyone who unzips the IPA. Treat that prefix as "publish this to the internet".

Authorization

RLS is the enforcement layer, not a backstop. Edge Functions call Postgres with the caller's JWT, not the service role, except for the narrow paths that genuinely need elevation (catalogue import, account deletion) — and those validate ownership explicitly first.

Input validation

Every Edge Function input, every AI response, and every sync payload is Zod-parsed at the boundary. Postgres CHECK constraints repeat the critical invariants (non-negative nutrients, quantity > 0, exactly one of food/recipe) so a bug in the app can't write nonsense.

Storage

Meal and label photos go in a private bucket, path-prefixed by user ID with a matching storage policy. Access is via short-lived signed URLs only. Set a retention policy — deleting scan images after the scan is confirmed reduces both the storage bill and the breach surface.

Rate limiting

Per-user and per-IP limits on the AI endpoints, enforced server-side before any spend. Without this, one script turns your model bill into an incident.

User rights

export-data and account-delete as first-class Edge Functions from the start. Deletion must cascade through storage objects too, not just rows — and it's an App Store requirement, not a nice-to-have.

10

Platform decisions — settled

These four were the open questions; all are now resolved, and each carries a consequence the build has to honour.

A · Backend Supabase

Postgres, Auth, Storage and Edge Functions. Consequence: RLS is the security boundary, so every migration ships with its policies and a test that proves user A cannot read user B's rows.

B · Food data USDA + Open Food Facts

Consequence: Open Food Facts is ODbL. The foods.license column is mandatory, in-app attribution is required, and derived database shares carry share-alike. USDA rows are public domain and unencumbered.

C · Offline Offline-first

SQLite is the source of truth; the server is a sync target. Consequence: every table needs client-generated UUIDs, updated_at and soft deletes from the first migration, and the UI reads only from the local database.

D · AI provider Claude

Behind the AIProvider interface, so it stays swappable. Opus 5 for both tasks to set the accuracy ceiling, then measure Haiku 4.5 on labels at roughly a fifth of the cost. Structured outputs via output_config.format, Zod-validated server-side.

Still open, but not blocking: whether exercise calories add back to the daily budget (shipping as a setting, default off), the free/premium boundary, and launch languages. Each can be answered during the phase that needs it.
